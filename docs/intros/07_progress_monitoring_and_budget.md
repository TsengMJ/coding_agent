# 07 進度監控、盲目重試與預算

## 問題

- **盲目重試**：同一個失敗的 patch 重送 5 次、同一個 diagnostics 跑 7 次，什麼都沒改。
- **時間用完還在調查**：b398 的逾時 run 最後 70 步都在追一個 export 測試，從沒收斂，最後被 50 分鐘上限截斷，連一個完整的修改都沒交出。
- **無限迴圈燒錢**：模型卡在某個模式裡一直呼叫工具。

## 業界怎麼做

- **mini-SWE-agent**：步數、成本、時間與「重複格式錯誤」都有上限。
- **SWE-bench Pro 論文**：各模型主要失敗類型不同，其中包含 context overflow 與「無止盡讀檔」。

## 1. 先看資料再設計（R7）

R1 標出 9 個「同一呼叫重複 ≥5 次」的 attempt。逐一看 trace 後發現**幾乎都是正常的**：每次編輯後重跑同一個檢查，或在編輯之間反覆跑 `diagnostics` / `git_status`。所以規則不能是「重複就擋」，而要是「**同樣失敗、中間什麼都沒變**就擋」。

## 2. ProgressMonitor

實作：[code/agent/progress.go](../../apps/agent/code/agent/progress.go)（`WrapToolCall`）。

### 規則

同一個呼叫（工具名稱 + 參數 JSON 完全相同）以**同樣方式**失敗：

| 次數 | 行為 |
|---|---|
| 第 1 次 | 正常 |
| 第 2 次 | 執行，結果尾端附註「和上一次一樣的失敗；不改東西再跑會被拒絕」 |
| 第 3 次 | **不執行**，回錯誤：「讀錯誤訊息、改參數或程式，或換方法」 |

### 「同樣方式失敗」怎麼判斷（失敗指紋）

```go
// volatile matches the parts of tool output that change between identical
// runs: numbers (durations, counts, line offsets, ports) and hex ids.
var volatile = regexp.MustCompile(`0x[0-9a-fA-F]+|[0-9a-f]{12,}|\d+(?:\.\d+)?`)
```

- 測試 / build 檢查：有失敗測試名單時，用**排序後的失敗測試名單**當指紋；否則用正規化後的輸出。
- 其他工具：錯誤狀態或 `Error` 開頭的輸出，數字與 hex 換成 `#` 後比較（測試時間 `0.53s` vs `0.61s` 不會被當成不同）。
- `execute` exit code 非 0 也算失敗。

### 什麼時候重置

- 新的使用者訊息；
- **成功的編輯**；
- **成功的 shell 指令**（例如裝了依賴之後重試是合理的）；
- 同一個呼叫成功了。

### 為什麼從對話推導、不存狀態

所有判斷都從 state 的訊息即時計算。好處：

1. checkpoint 還原、server 重啟後一樣有效；
2. 可以對歷史 trace **離線重播**，在不花錢的情況下估計它會介入幾次。

### 離線重播結果

28 個歷史 attempt：拒絕 2 次，**都在 bd80**——同一個完整 `test/controllers.js` 在沒改任何東西下以同樣失敗跑了 3 次，正是「看到失敗、說無關」的那次；附註 5 次。

### 刪掉的規則

「3 次編輯之後失敗指紋都不變，提示換策略」也實作並重播了，結果 **0 次觸發**：b398 的長 debug 每次改用不同指令（`run_tests` 加 filter 與 `mocha --grep` 交替），指紋都不同。依「從未觸發就刪掉」的原則移除。

## 3. 預算提醒

實作：[code/agent/budget.go](../../apps/agent/code/agent/budget.go)（只在 headless）。

- 用掉 **80%** 的 deadline（ctx 的 deadline）或步數上限之後，每次請求尾端加一則 request-only 訊息（`lc_source: budget`）：「完成手上的修改、跑一次相關測試、給最終回覆並說明哪些沒驗證，不要開新的調查」。
- 放在尾端、不寫進 state：**不破壞 cache 前綴**（見 05）。
- 步數算的是「最後一則使用者訊息之後的 assistant 回覆數」。
- 測試：時間 78% 不提示、80% 提示；步數 8/11 不提示、8/10 提示；沒有上限不提示。
- 最終評測只在 b398 t0 觸發（14 次），那次仍逾時——唯一的案例沒看到效果，保留但標記為「效果未證實」。

## 4. 硬性上限

| 上限 | 位置 | 預設 |
|---|---|---|
| 步數（recursion limit） | [agent/loop.go](../../apps/agent/agent/loop.go) | `runtime.DefaultRecursionLimit`，可依 run 設定 |
| quill `-timeout` | CLI | 逾時 exit 124，Ctrl-C exit 130 |
| quillbench 每題時間 | 官方 locked protocol | 50 分鐘 |
| quillbench 每題成本 / 步數 | `-max-cost` / `-max-steps` | $3 / 250 步 |
| 驗證閘門擋下次數 | verify.go | 2 次 |

quillbench 的成本上限由 `meteredModel` 實作：包在模型外面，每次呼叫後累加成本，超過就讓下一次呼叫失敗，錯誤分類成 budget。

## 5. Prompt 層的配合

system prompt 依模式替換失敗處理段落：

- interactive：「第三次嘗試時停下來問使用者；發現自己在繞圈就求助」。
- headless：「重複失敗後換一個允許的方法；沒有就回報阻礙與已完成的部分」。

程式的規則（第 3 次拒絕）與 prompt 的指引一致，prompt 負責「為什麼」，程式負責「一定會發生」。

## 面試講法

> 「我沒有用『重複就擋』，因為看了 trace 發現大部分重複是正常的：改完檔案重跑同一個測試。規則是：同一個呼叫、同樣的失敗、中間沒有任何編輯或指令，第二次附註、第三次直接不執行。『同樣的失敗』用正規化後的輸出或失敗測試名單當指紋，去掉時間、行號這些每次都會變的數字。整個判斷都從對話推導，所以可以拿歷史 trace 離線重播；重播結果顯示它只會在 bd80 那次『看到失敗卻說無關、原地重跑三次』的地方介入，正好是我想擋的。」

可能的追問：

- **為什麼是第 3 次不是第 2 次？** 第 2 次有可能是 flaky 或暫時性錯誤；附註先給機會，第 3 次才拒絕。
- **模型改一個無關的參數繞過怎麼辦？** 參數不同就是不同呼叫，這是刻意的：只要有任何改變就該讓它試，規則的目標是擋「完全沒改變」的重試。
- **預算提醒為什麼不直接停？** 直接截斷會留下半套修改；提醒讓 agent 收尾、交出可評分的 patch 與誠實的最終說明。
